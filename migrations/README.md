# Migrations

Plain SQL migrations applied by `scripts/migrate-safe.sh` in lexical order.
Each file's basename is its version key in `schema_migrations`.

## Naming

```
NNNN_short_description.sql
```

- `NNNN` is a zero-padded four-digit sequence.
- `short_description` is snake_case.
- One logical change per file.

## Rules

- Run real database migrations only through `just db-migrate-dev` or
  `just db-migrate-deploy`; both call `scripts/migrate-safe.sh` and take a
  backup first.
- Migration SQL runs through `psql --single-transaction`. DDL that requires its
  own transaction, such as `CREATE INDEX CONCURRENTLY`, needs a separate
  operator path before it can be introduced.
- The migration set starts from a canonical schema baseline. After the initial
  public baseline is cut and a migration is applied to a persistent database,
  add a new migration instead of editing history.
- Numbering after the baseline starts with `0003_*`.
- Source ids are explicit, permanent, and never reused. Adding a source after
  the baseline: assign the next never-used id in the registry, regenerate the
  `0002` fresh-database seed with `just gen-source-artifacts`, and add an
  idempotent forward migration for databases that already applied the previous
  `0002`. The regenerated `0002` covers fresh databases; the forward migration
  covers existing ones.
- Retiring a source leaves its id unused. Add a guarded forward migration that
  refuses to delete evidence, removes only disposable operational or derived
  state, then deletes the source row. Never close or reuse the resulting gap.
- Materialized view refresh strategies should be documented in the migration
  that creates the view and exercised by a test.
- Before applying `0019`, stop all Monitor processes and prevent old binaries
  from restarting until the new classifier completes the full orphan recheck.
  Follow the stop/migrate/start procedure in `docs/operations.md`; the retry
  booleans do not identify which binary consumed them.

## Current Migrations

The live on-disk migration set contains the canonical baseline, generated source
seed, and append-only forward migrations.

Creates producer base tables, chain sidecars, poll cursors (incl. `target_height`), read-model tables, source-health invariants (incl. strict/weak orphan counters), Bitcoin Core backbone state, the complete-canonical tree index, event-level pool attribution, the Hathor reward-output columns, and the `rsk_reclassify_watermark` singleton directly. | `0007_support_partial_child_evidence.sql` | Makes child evidence independently nullable, adds authenticated child header and `nBits`, preserves normalized and full-transaction parent-coinbase evidence, replaces the legacy composite identity with exact and partial identities, and adds source-row-grained historical provenance with an explicit pinned-commit or operator-CSV reference plus its durable parent/cascade reconcile queue. | `0008_add_error_block_parent_kind.sql` | Adds the catalogued `error_block` full-PoW consensus-invalid state to base and derived parent-kind constraints, including its pinned-catalogue height source and primary rejection token. |

| `0011_track_core_cache_orphan_rechecks.sql` | Separates the durable pending-coverage retry from the durable full-orphan-recheck retry, so ordinary tip advances do not rescan already classified orphans. |

| `0013_allow_live_error_block_height_sources.sql` | Permits a live Core-derived predecessor height for `error_block` rows while retaining the catalogue height source as the fallback. |

| `0020_add_qbit_source.sql` | Idempotently converges live source `auxpow:qbit` on permanent id 36 for databases that applied the earlier generated seed. Fresh databases already contain the row through `0002`. |
| `0021_add_capture_error.sql` | Adds the producer-owned `capture_error` table (`(source_id, height)` primary key, optional 32-byte `block_hash`, `error_kind`, diagnostic `detail`, `first_seen_at`/`last_seen_at`). It records a height a producer could not capture, which the monotonic `poll_cursor` cannot express and which the derived `source_health` cannot carry. Written before the failing height returns and cleared only when that same height is reprocessed successfully; `/api/v1/sources` reports the lowest unresolved height per source. |
| `0022_add_child_displacement.sql` | Adds nullable `child_displaced_at` and `child_displaced_by` to `merge_mining_event`: the time a producer observed the child chain no longer carrying that block at its height, and the internal-order hash of the block carried there instead. Three CHECK constraints (32-byte hash, both columns set or both null, a block with a known hash is never displaced by itself) are added `NOT VALID` so the file's exclusive lock is not held across a full-table scan; they are enforced for every new write immediately. A displaced event stays active for every Bitcoin-side aggregate; revocation remains reserved for bad evidence. `mmm-store::record_child_chain_block` is the one writer; the bitcoind-family runner and the Elastos producer call it for every processed height. |
| `0023_validate_child_displacement.sql` | Validates the three `0022` constraints in one statement (one table scan) in their own transaction, where `VALIDATE CONSTRAINT` takes only `SHARE UPDATE EXCLUSIVE` and capture and API reads continue. Cannot fail: every pre-`0022` row has both columns null and every later row was checked on write. |
| `0024_restore_hathor_displaced_events.sql` | Restores every event revoked `hathor_superseded` or `hathor_voided`; a superseded event also records its displacement by the block the chain carried when it was revoked (first seen no later than the revocation and not revoked before it; `discovered_at` never moves, unlike `confirmed_at`), while a voided event names no replacement. Completes any leftover `supersede` marker the same way; a child-chain replacement is displacement, not bad evidence. Prints before/after counts as notices. Restored events change their parents' read model: run `just reconcile-read-model --all --source auxpow:hathor` and `just rebuild-source-health` afterwards with the new binary; see `docs/operations.md`. |
| `0025_retire_pending_supersede.sql` | Deletes the `supersede` rows of `poll_pending_reconcile` and drops its `kind`, `new_child_block_hash` and `superseded_event_ids` columns and the per-source index: the table holds one held height per source, unique on `(source_id, height)`. An older binary reads the dropped columns, so it must not run after this migration. |
| `0026_add_child_chain_head.sql` | Adds `child_chain_head`, one row per `(source_id, child_height)` with the block hash a producer last observed there, the parent its proof named, an outcome and the observation time, so a trailing rescan can decide from one block-hash lookup whether the height changed. No backfill; the first rescan window fills it. |
| `0027_schedule_core_rechecks_by_generation.sql` | Replaces `reclassification_needed` and `orphan_recheck_needed` on `bitcoin_core_header_cache_state` with a pending generation and scope, an acknowledged generation, and the bound pass with its cursor, consumed by `reclassify-unknown-parents --scheduled` instead of inside producer startup. A set boolean converts to pending generation 1. A migration that needs a recheck runs `UPDATE bitcoin_core_header_cache_state SET recheck_pending_generation = recheck_pending_generation + 1, recheck_pending_orphans = TRUE, recheck_pending_sources = CASE WHEN recheck_pending_sources IS NULL OR (recheck_pass_generation IS NOT NULL AND recheck_pass_sources IS NULL) THEN NULL ELSE (SELECT array_agg(DISTINCT s) FROM unnest(recheck_pending_sources \|\| COALESCE(recheck_pass_sources, '{}') \|\| ARRAY['auxpow:hathor']) AS s) END, recheck_pass_generation = NULL, recheck_pass_orphans = NULL, recheck_pass_sources = NULL, recheck_cursor_height = NULL, recheck_cursor_id = NULL` (`NULL` sources means every source, so the pass's `NULL` widens the scope only while a pass is bound, `recheck_pass_generation IS NOT NULL`; with no pass the columns are `NULL` because there is nothing to fold; clearing the pass and folding its sources into the pending scope restarts a pass in flight, which a rule change that alters verdicts already given requires) and states so in its header. |
| `0028_add_reconcile_queue_expand_unchanged.sql` | Adds `expand_unchanged` to `bitcoin_core_reconcile_queue`. A strict primary now settles its own row in the transaction that commits its reconcile: it becomes an expansion row when the reconcile changed it or the flag is set, and is retired otherwise, so a scheduled recheck's cascade stops at the first unchanged descendant; a suffix replacement's seeds carry the flag, which is never inherited by the dependents an expansion enqueues. Rows queued before the migration were all suffix seeds and convert to TRUE. |
| `0029_drop_body_invalid_stale.sql` | Drops the obsolete display-annotation table after body-invalid parents move into the reviewed error catalogue. Run through the backup-first migration workflow; child events and publication provenance are unaffected. |

`0002_seed_sources.sql` is only for fresh/reset databases. It intentionally
raises if `source` is already populated, so a non-reset database fails cleanly
after the wrapper backup instead of appending rows with wrong ids.

If any migration fails, both dev and deploy mode restore from the just-created
backup and exit non-zero.

Manual restore uses the same compatibility filter printed by the wrapper:

```sh
gunzip -c '<backup-file>' | sed '/^SET transaction_timeout/d' | psql --set ON_ERROR_STOP=on
```

## Reset Path

Fresh, CI, and throwaway databases use the explicit reset path. `just clean`
does not remove the Postgres volume.

1. Confirm the database is disposable local state.
2. `CONFIRM_DB_RESET=1 just db-reset` (runs `just db-backup` first).
3. `just db-up`
4. `just db-migrate-dev`
5. `just rebuild-source-health`
6. Re-run required historical backfills or live-test backfill commands.

## Postgres Type Choices

| Concept | Postgres representation | Notes |
|---------|----------------|-------|
| Surrogate keys | `BIGINT GENERATED ALWAYS AS IDENTITY` | SQL-standard identity form. |
| Epoch timestamps | `BIGINT` | Avoids 2038 wraparound. |
| Validation flags | `BOOLEAN` | |
| Hashes, headers, and proofs | `BYTEA` | Header hashes, coinbases, and merkle proofs. |
| Structured metadata | `JSONB` | Pool tags and payout addresses. |

`CHECK` constraints encode source vocabulary, parent-kind vocabulary, chain
sidecar invariants, byte-length invariants for hashes and headers, and
read-model consistency constraints. Producer write SQL lives in
`crates/mmm-store/src/lib.rs`; derived-state writes go through
`crates/mmm-read-model`.
