# Migrations

Plain SQL migrations applied by `scripts/migrate-safe.sh` in lexical order.
Each file's basename is its version key in `schema_migrations`.

## Naming

```
NNNN_short_description.sql
```

- `NNNN` is a zero-padded four-digit sequence.
- `short_description` is snake_case.
- One logical change per file.

## Rules

- Run real database migrations only through `just db-migrate-dev` or
  `just db-migrate-deploy`; both call `scripts/migrate-safe.sh` and take a
  backup first.
- Migration SQL runs through `psql --single-transaction`. DDL that requires its
  own transaction, such as `CREATE INDEX CONCURRENTLY`, needs a separate
  operator path before it can be introduced.
- The migration set starts from a canonical schema baseline. After the initial
  public baseline is cut and a migration is applied to a persistent database,
  add a new migration instead of editing history.
- Numbering after the baseline starts with `0003_*`.
- Source ids are explicit, permanent, and never reused. Adding a source after
  the baseline: assign the next never-used id in the registry, regenerate the
  `0002` fresh-database seed with `just gen-source-artifacts`, and add an
  idempotent forward migration for databases that already applied the previous
  `0002`. The regenerated `0002` covers fresh databases; the forward migration
  covers existing ones.
- Retiring a source leaves its id unused. Add a guarded forward migration that
  refuses to delete evidence, removes only disposable operational or derived
  state, then deletes the source row. Never close or reuse the resulting gap.
- Materialized view refresh strategies should be documented in the migration
  that creates the view and exercised by a test.

## Current Migrations

The live on-disk migration set contains the canonical baseline, generated source
seed, and append-only forward migrations.

| File | Notes |
|------|-------|
| `0001_canonical_schema.sql` | Canonical schema baseline. Creates producer base tables, chain sidecars, poll cursors (incl. `target_height`), read-model tables, source-health invariants (incl. strict/weak orphan counters), Bitcoin Core backbone state, the complete-canonical tree index, event-level pool attribution, the Hathor reward-output columns, and the `rsk_reclassify_watermark` singleton directly. The watermark singleton is dropped again by `0009` and is not part of the live schema. |
| `0002_seed_sources.sql` | Registry-generated fresh-database seed for all 33 `source` rows from `crates/mmm-capture/src/source_registry`, using explicit permanent ids across live, historical, partial, surveyed, and catalogued lifecycles. Id 32 is retired; the identity restarts at 35. The seed raises if `source` is already populated. Generated by `just gen-source-artifacts`; do not edit by hand. |
| `0003_add_elcash_source.sql` | Idempotent forward insertion of historical source `auxpow:elcash` for databases that applied the pre-Elcash `0002`. Fresh databases already contain id 34, so this is a no-op there. This exact migration is retained because production applied it on 2026-06-26. |
| `0004_remove_mazacoin_source.sql` | Verifies that the historical Elcash insertion converged on permanent id 34, then idempotently retires Mazacoin source id 32 on upgraded databases. It refuses removal if event or attestation evidence exists, then removes disposable source state before deleting the source row. Fresh databases already omit id 32. |
| `0005_rename_excluded_orphan_class.sql` | Idempotently renames the `block.btc_orphan_class` excluded verdict from `btc_stale_excluded` to `excluded`, matching the same rename in the research repo's `btc_stale_relevance` vocabulary. Rewrites existing rows, then drops and re-adds the CHECK constraint (located by definition text, not by its autogenerated name). |
| `0006_add_known_stale_block.sql` | Adds the operator-imported `known_stale_block` membership table (hash PK in internal byte order, advisory `btc_height`, `source_label`, `imported_at`), consulted at `block.btc_orphan_class` derivation so a known stale is `excluded` rather than mislabelled strict/weak. Loaded by `import-known-stales`. |
| `0007_support_partial_child_evidence.sql` | Makes child evidence independently nullable, adds authenticated child header and `nBits`, preserves normalized and full-transaction parent-coinbase evidence, replaces the legacy composite identity with exact and partial identities, and adds source-row-grained historical provenance with an explicit pinned-commit or operator-CSV reference plus its durable parent/cascade reconcile queue. Fails before altering the schema if legacy rows duplicate an exact source/hash identity. |
| `0008_add_error_block_parent_kind.sql` | Adds the catalogued `error_block` full-PoW consensus-invalid state to base and derived parent-kind constraints, including its pinned-catalogue height source and primary rejection token. |
| `0009_drop_rsk_reclassify_watermark.sql` | Drops the `rsk_reclassify_watermark` singleton created by `0001`, retiring the `reclassify-pools` RSK skip. Continuous RSK capture normally changes the active-set fingerprint every block, so the skip rarely avoided a run while its start and end fingerprints each scanned the RSK partition. Activate the watermark-free binary and confirm no older `reclassify-pools` process is running before applying it; see `docs/operations.md`. Idempotent (`IF EXISTS`); no foreign keys reference the table. Back-to-back reclassification runs now always rescan. |
| `0010_add_bitcoin_core_header_cache.sql` | Adds `bitcoin_core_header`, the sparse canonical header cache populated from the required Bitcoin Core node. It marks difficulty boundaries final only after re-reading them 100 blocks deep, while refreshing the shallow current epoch and synced-tip horizon for nBits and timestamp classification. |
| `0011_track_core_cache_orphan_rechecks.sql` | Separates the durable pending-coverage retry from the durable full-orphan-recheck retry, so ordinary tip advances do not rescan already classified orphans. |
| `0012_add_bitcoin_core_reconcile_queue.sql` | Adds generation-protected two-phase work for atomic near-tip Bitcoin Core canonical suffix replacement. Each row persists primary reconciliation separately from dependent expansion, and generation checks keep newer work for the same hash queued across concurrent repair or replay. |
| `0013_allow_live_error_block_height_sources.sql` | Permits a live Core-derived predecessor height for `error_block` rows while retaining the catalogue height source as the fallback. |
| `0014_add_error_block_historical_provenance.sql` | Allows the retained `error-block-observations` publication scope to record its actual `error_block` classification in source-row provenance; normal historical taxonomy is unchanged. |

`0002_seed_sources.sql` is only for fresh/reset databases. It intentionally
raises if `source` is already populated, so a non-reset database fails cleanly
after the wrapper backup instead of appending rows with wrong ids.

If any migration fails, both dev and deploy mode restore from the just-created
backup and exit non-zero.

Manual restore uses the same compatibility filter printed by the wrapper:

```sh
gunzip -c '<backup-file>' | sed '/^SET transaction_timeout/d' | psql --set ON_ERROR_STOP=on
```

## Reset Path

Fresh, CI, and throwaway databases use the explicit reset path. `just clean`
does not remove the Postgres volume.

1. Confirm the database is disposable local state.
2. `CONFIRM_DB_RESET=1 just db-reset` (runs `just db-backup` first).
3. `just db-up`
4. `just db-migrate-dev`
5. `just rebuild-source-health`
6. Re-run required historical backfills or live-test backfill commands.

## Deferred Objects

Some planned objects are deliberately absent from the current schema. They
should land together with their owning consumers:

| Object | Lands with |
|--------|------------|
| `tip_state` and full live-chaintip observation semantics | the Bitcoin Core live-chaintip producer |
| `v_timeline_daily`, `v_pool_period_stats`, `v_near_miss_rollup` | API, UI, or analytics consumers |

## Postgres Type Choices

| Concept | Postgres representation | Notes |
|---------|----------------|-------|
| Surrogate keys | `BIGINT GENERATED ALWAYS AS IDENTITY` | SQL-standard identity form. |
| Epoch timestamps | `BIGINT` | Avoids 2038 wraparound. |
| Validation flags | `BOOLEAN` | |
| Hashes, headers, and proofs | `BYTEA` | Header hashes, coinbases, and merkle proofs. |
| Structured metadata | `JSONB` | Pool tags and payout addresses. |

`CHECK` constraints encode source vocabulary, parent-kind vocabulary, chain
sidecar invariants, byte-length invariants for hashes and headers, and
read-model consistency constraints. Producer write SQL lives in
`crates/mmm-store/src/lib.rs`; derived-state writes go through
`crates/mmm-read-model`.
